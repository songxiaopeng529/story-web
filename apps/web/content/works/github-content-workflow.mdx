这不是一个独立发布的软件，而是 story-web 内的一项内容实验：用尽量少的状态，把“写完一份 Markdown”连接到“得到一个可审阅的网页”。

## 目标与边界

流程首先服务单人创作，因此刻意不包含账户、角色权限和在线协同编辑。当前只验证三件事：

1. 元数据错误能否在合并前被发现；
2. 内容变更能否像代码一样看到清晰差异；
3. 页面预览能否与最终生产构建保持一致。

<Callout type="warning" title="它还不是 CMS">
  手机写作、定时发布和多人审批都不在当前范围内。如果这些需求变得频繁，未来的管理端会接入同一份内容契约，而不是另起一套数据模型。
</Callout>

## 文件就是状态

流程不在数据库里维护一列发布状态，而是使用 Frontmatter 中的 `published`。构建器只收集字段合法且公开的文件：

```ts
const visibleEntries = entries
  .filter((entry) => entry.meta.published)
  .sort((a, b) => b.meta.date.localeCompare(a.meta.date));
```

这种实现不复杂，却能保证列表、详情、RSS 与 sitemap 使用同一套判断。

## 校验清单

- [x] 标题、摘要、日期和内容类型必填
- [x] slug 从文件名派生，避免重复维护
- [x] 文章与作品分别验证扩展字段
- [ ] 检查正文中的站内链接是否存在
- [ ] 检查画板引用是否有对应的静态预览

| 失败场景           | 期望行为                         |
| ------------------ | -------------------------------- |
| 日期格式无效       | 构建立刻失败并指出文件           |
| slug 重复          | 阻止生成冲突路由                 |
| `published: false` | 开发环境可检查，生产列表不公开   |
| 画板缺失           | 提供明确错误，而不是留下空白区域 |

## 为什么值得单独记录

工作流也是作品的一部分。页面只能展示最后的画面，内容协议决定这个站点能否稳定生长。把这些取舍写下来，可以在未来引入管理端、数据库或不同部署环境时，判断哪些边界应该保留，哪些只是 V1 的临时实现。
