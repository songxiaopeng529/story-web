个人网站常常从一个页面开始，最后却变成三个互相不同步的系统：简历在文档里，文章在内容平台里，作品说明散落在网盘和聊天记录中。真正难维护的不是页面，而是这些内容之间没有共同的版本。

我为这个站点设定了一条简单规则：**仓库里的文件就是内容真源**。页面、索引、RSS 和站点地图都由它们构建出来，不再维护另一份后台副本。

<Callout type="note" title="这里的“真源”是什么意思？">
  如果网站显示的内容与仓库文件不一致，以仓库里经过提交和审阅的版本为准。构建产物可以删除并重新生成。
</Callout>

## 一份内容的生命周期

一篇文章从草稿到发布，只需要经历几个明确状态：

- [x] 在本地创建 Markdown 或 MDX 文件
- [x] 补全 Frontmatter，并让构建脚本校验它
- [x] 通过分支和 Pull Request 查看变更
- [ ] 在 Preview 环境确认真实页面效果
- [ ] 合并到主分支并发布

内容也遵守同样的生命周期：从 Markdown 或 MDX 开始，经由构建校验生成页面与索引；当需要空间化表达时，再将它作为独立作品逐步补充，而不是把静态资产堆进站点目录。

## 元数据要少，但要稳定

Frontmatter 不应该变成一张无止境扩张的表单。V1 只保留列表、SEO 和发布流程确实需要的字段：

| 字段                    | 用途           | 维护方式         |
| ----------------------- | -------------- | ---------------- |
| `title` / `description` | 页面标题与摘要 | 每篇必填         |
| `date` / `updated`      | 排序与更新时间 | 使用 ISO 日期    |
| `tags`                  | 轻量归类       | 保持少量、可复用 |
| `published`             | 控制公开状态   | 草稿设为 `false` |
| `featured`              | 首页精选       | 只标记少数内容   |

slug 直接来自文件名，这样就不会同时维护“文件路径”和“路由字段”。如果未来确实需要改 URL，再显式增加重定向，而不是提前引入复杂的永久 ID。

## 为什么不是先做一个后台

后台会带来账户、权限、数据库、编辑器和部署等一整套运行时问题。它们当然有价值，但对于一个刚开始积累内容的个人站点，并不是第一阶段的必要条件。

Git 已经提供了当前真正需要的能力：历史、差异、分支和回退。等到手机编辑、多人协作或定时发布成为高频需求时，再让后台作为新的内容入口接入，而不是替换现有文件协议。

## 保持迁移出口

把内容留在 Markdown 还有一个安静但重要的好处：它不依赖当前页面实现。即使未来从 Next.js 迁移到另一套框架，正文、Frontmatter 和画板源文件仍然可以继续使用。

这不是为了追求“永远不改技术栈”，而是让每次改变都只支付必要的成本。关于当前实现，可以继续看作品页里的 [story-web](/works/story-web)。
